# Pixel Formula Roller — BA Requirements Review
**Reviewer:** Senior BA/Product Analyst
**Review date:** 2026-04-26
**Documents reviewed:** `CLAUDE.md`, `docs/specs/app-spec.md`, STORY-001 through STORY-008

---

## Section 1 — Completeness

**Finding 1.1 — Bluetooth permission denial is unhandled.**
No story or spec section describes what happens when the browser's BLE permission prompt is dismissed or denied by the user. `requestPixel()` will throw (or return nothing) in that case. There is no acceptance criterion covering: the error state shown to the user, how they can retry, or how to guide them if BLE is unavailable on their browser (e.g. Firefox, Safari without Bluefy). This gap exists in STORY-003 and STORY-007.

**Finding 1.2 — Manual result entry fallback is promised but never specified.**
Section 7 of the spec and STORY-006 both mention "allow manual entry fallback (type the result)" as the response to a missing or mid-roll-disconnected die, but there is no wireframe, no acceptance criterion, no data flow, and no story that defines what that UI looks like or how manually entered values are fed into `evaluateFormula()`. This is an incomplete feature promise, not a deferred one.

**Finding 1.3 — Roll initiated from Main Screen is underspecified.**
The spec states (§ 6.1): "Tapping a saved formula card → opens Formula Screen with formula pre-loaded and dice glowing." This implies dice begin glowing immediately when the formula screen loads via card tap — before the user presses ROLL. No story captures the logic for this auto-glow-on-load path, and STORY-006 only wires the explicit ROLL button. If the intent is truly auto-glow, STORY-005 and STORY-006 both need acceptance criteria for it. If the intent is just "pre-loaded" (fields populated, no auto-glow), the spec wording must be corrected.

**Finding 1.4 — No empty-formula guard on the Roll button.**
STORY-005 specifies SAVE validates that a formula is non-empty and parseable, but neither STORY-005 nor STORY-006 specifies what happens when a user clicks ROLL with an empty or invalid formula. This is a distinct path from a parse-fail-on-blur.

**Finding 1.5 — History entry when closing vs. dismissing the Result Panel is ambiguous for "Roll Again".**
STORY-006 states history is written when the user closes the Result Panel via [✕]. It is silent on whether [Roll Again] also writes the previous result to history before starting the next roll, or discards it. A user who never presses [✕] and keeps pressing [Roll Again] would accumulate zero history entries under the current spec.

**Finding 1.6 — No story covers the PWA manifest / installability.**
CLAUDE.md and app-spec §9 defer the "offline PWA install prompt" to post-MVP, which is reasonable — but there is no story that creates a valid `manifest.json` or `service-worker`. Without a manifest, the app cannot be installed to a home screen, which is a meaningful loss for a mobile-first app used at a game table. This should at minimum be a documented known gap with an explicit decision, not a silent omission.

**Finding 1.7 — Theme selector has no defined colour palette.**
The spec defines `theme: "pixel-dark" | "pixel-light"` in the data model and the Settings screen lists it as a control, but there is no definition of what either theme actually looks like (no colour tokens, no Tailwind config entries). STORY-007 marks it as a "stretch goal, can stub." However, if the type is already in the persisted store, a light-theme user who later gets the feature will see it silently ignored. The stub should at minimum render the dark theme unconditionally and leave the toggle disabled/hidden so no invalid state is persisted.

**Finding 1.8 — Battery level sourcing is undefined.**
`PixelEntry` includes `batteryLevel` and the Settings screen AC requires showing "battery %", but STORY-003 does not include an acceptance criterion for subscribing to battery events from the SDK, nor is there any mention of how frequently the value is refreshed. If the SDK does not push battery events continuously, a stale or always-zero value will be shown.

**Finding 1.9 — No defined maximum for formula complexity.**
There is no upper bound on the number of dice, modifier size, or formula string length. The formula text field is a free-text input. A formula like `999d20kh1+999d12kl1+500` is technically valid but could produce a confusing UX or performance issue during roll collection (999 individual BLE events expected). No AC addresses this.

## Section 2 — Consistency

**Finding 2.1 — Die type naming mismatch between spec and types.**
The spec (§ 4) exposes `pixel.dieType` as `"d00"` (percentile). The formula language (§ 5) uses `"d%"`. `RequiredDie.dieType` in STORY-002 uses `"d100"`. The Formula Screen picker (§ 6.2) labels the row `"d%"`. `DieRollResult.dieType` is typed as `string`. Three different tokens for the same die type (`"d00"`, `"d%"`, `"d100"`) will require implicit conversions at every boundary between the BLE service, the formula parser, and the UI — a guaranteed source of bugs. A canonical name must be chosen and enforced throughout.

**Finding 2.2 — `RollHistoryEntry.modifier` is a scalar; compound formulas can have multiple modifiers.**
The spec data model has a single `modifier: number` on `RollHistoryEntry`. The formula language explicitly supports formulas like `2d20kh1+1d8+3d6kl1` where each group could in principle have its own flat component, and there is no constraint that only one flat modifier exists per formula. When `rpg-dice-roller` parses a formula, the "modifier" is effectively the sum of all numeric constants. This works numerically but makes the Result Panel display ("+ 5 (modifier)") potentially misleading if the formula had, e.g., `+3` and `+2` as separate terms. This needs a deliberate design decision, not an implicit one.

**Finding 2.3 — `ParsedFormula` type is referenced but never defined.**
STORY-002 exports `parseFormula(): ParsedFormula | null` but `ParsedFormula` is not defined anywhere in the types listed in STORY-002 or the spec. Only `RequiredDie`, `DieRollResult`, `EvaluationResult`, and `PickerState` are defined. The developer will have to invent this type, with no agreed shape.

**Finding 2.4 — STORY-005 delegates Roll to STORY-006 but owns the Roll button.**
STORY-005 AC says "[SAVE]: validate → persist → navigate to Main Screen (see STORY-006 for Roll)" and has no AC for the Roll button whatsoever. STORY-006 AC says "Wire the ROLL button." This creates an implementation ambiguity: does STORY-005 render a disabled/stub Roll button, or no button, or does it leave a TODO placeholder? A developer building STORY-005 in parallel with STORY-006 has no guidance. The button's visual presence and disabled state should be specified in STORY-005.

**Finding 2.5 — Open Question #1 is referenced with inconsistent section pointers.**
CLAUDE.md Open Questions list item #1 says "check before STORY-003." The spec (§ 10) says "Check SDK source before STORY-004." These are different stories. The discrepancy will cause one document to be ignored.

**Finding 2.6 — Section numbering error in the spec.**
The spec jumps from § 9 (MVP Scope) to § 11 (Deployment), skipping § 10 entirely — then places Open Questions at § 10 after § 11. This is a markdown authoring error that will confuse anyone reading the document linearly.

## Section 3 — Ambiguities

**Finding 3.1 — "Long-press OR swipe / kebab menu" is three different patterns.**
STORY-004 AC says "Long-press OR swipe → reveal Edit / Delete options" and the spec adds "kebab menu" as a third option. These are meaningfully different interaction models with different implementation costs and different suitability on desktop vs. mobile. The choice must be made before implementation. A long-press with a 500ms threshold is notoriously hard to test and inaccessible. "Kebab menu" is the most portable. No decision has been captured.

**Finding 3.2 — "Dice glowing" during simultaneous multi-die rolls is undefined.**
STORY-006 says "Call `glowDie()` on each required die in sequence (or simultaneously if formula allows parallel rolls)" without defining what "formula allows parallel rolls" means or how that determination is made. All current formula examples could be rolled simultaneously since all dice are independent. The sequential-vs-parallel glow strategy has significant UX implications (is the user expected to roll all dice at once, or one at a time?) and must be specified explicitly.

**Finding 3.3 — "Relative timestamp" format is unspecified.**
STORY-004 AC requires "relative timestamp ('2 min ago')" in history entries. No library is specified (e.g. `date-fns/formatDistanceToNow`, `dayjs`, or a custom function). The exact thresholds and strings are undefined (e.g. "just now", "1 min ago" vs "a minute ago", how to handle > 1 day). This is untestable as written.

**Finding 3.4 — Keep modifier N input has no defined validation range.**
The formula screen has a Keep [N] numeric input per die row. There is no AC specifying: minimum value (1?), maximum value (≤ count?), what happens if N > count, or whether N is validated on blur or on change. `2d6kh3` is an invalid formula (keep 3 of 2 dice) and `rpg-dice-roller` may or may not handle it gracefully.

**Finding 3.5 — "Confirm before delete" is under-specified in both STORY-004 and STORY-005.**
Both stories mention a "confirmation dialog" for delete, but neither specifies the dialog text, the confirmation button label, whether it is a native `window.confirm()` call or a custom modal, or what happens to any in-progress roll state when deletion occurs from the Formula Screen.

**Finding 3.6 — STORY-004 history entry content contradicts the spec.**
STORY-004 AC says each history entry shows "individual die results, total, relative timestamp." The spec wireframe (§ 6.1) shows only "formula label/string, total result, timestamp" — no individual die results in the history list. These cannot both be right. Showing full per-die breakdowns in the compact history list has major layout implications.

**Finding 3.7 — "Inline bottom sheet on mobile, modal on desktop" for the Result Panel.**
STORY-006 specifies the Result Panel renders as a bottom sheet on mobile and a modal on desktop, but there is no breakpoint value specified, no accessibility requirements (focus trap, aria-modal, dismiss on backdrop click), and no guidance on the transition animation. This is underspecified for implementation.

## Section 4 — Gaps in User Flows

**Finding 4.1 — Back navigation mid-roll is not addressed.**
If a user presses [← Back] while dice are glowing and the app is awaiting roll events, there is no defined behaviour. The glow command will have been sent; the die will keep glowing. Event listeners will still be active. The roll result slot will be abandoned. No story cancels pending rolls or cleans up listeners on unmount/navigation.

**Finding 4.2 — The "new formula" save flow has a name prompt gap.**
The spec says "Prompt for a name if none entered" on Save. STORY-005 says the name field is pre-filled when editing but says nothing about what happens to a new formula with a blank name field — is it an inline validation error, a separate dialog prompt, or does it auto-generate a name from the formula string? Three different behaviours are all consistent with the current wording.

**Finding 4.3 — Navigating to `/formula/:id` for a non-existent ID has no error path.**
If a user bookmarks `/formula/abc123` and then that formula is deleted, the route will load with a missing ID. No story defines what happens: 404 page, redirect to Main, toast + redirect? This is a real case given local storage can be cleared independently of navigation history.

**Finding 4.4 — Bluetooth on iOS (Bluefy) has no dedicated UX path.**
The spec notes that iOS requires Bluefy. When the app loads in Safari on iOS, Web Bluetooth will be unavailable. There is no acceptance criterion for detecting this condition and showing a user-friendly message ("Please open this app in Bluefy to use Bluetooth features") rather than silently failing when Connect is tapped. The dice-free path (manual entry fallback, Finding 1.2) is also unspecified, which means iOS users have no viable workflow documented.

**Finding 4.5 — No offline / local storage quota error handling.**
The app uses local storage exclusively. Local storage has a ~5 MB limit that varies by browser and device. There is no AC in any story for handling a `QuotaExceededError` when saving a formula or writing a history entry. On a device that has hit the limit, saves will silently fail.

**Finding 4.6 — Formula Screen accessed via card tap vs. [+ New] diverges mid-flow.**
When a user taps a saved formula card, they land on `/formula/:id`. If they edit the formula text but do not save, pressing [← Back] discards changes silently — there is no "unsaved changes" warning. The same gap exists for [+ New]. This is a standard form-guard pattern that is entirely absent from the requirements.

**Finding 4.7 — Settings screen [← Back] destination is hardcoded.**
STORY-007 says "[← Back] → navigate to Main Screen." If the user navigated to Settings from a formula screen (unlikely with current nav, but possible if the Settings button is on all screens), they lose their navigation context. Using `navigate(-1)` instead of a hardcoded route is a safer default, but neither approach is specified.

## Section 5 — Risk Areas

**Finding 5.1 — Web Bluetooth roll event deduplication is unaddressed.**
Pixels dice can fire multiple roll events for a single physical roll (e.g. a `rolling` state event followed by a `rolled` state event). The spec mentions subscribing to `onRollState` / `onRoll` but STORY-003 does not specify which event type is used as the definitive result, nor how duplicate events for the same roll are filtered. Without deduplication, the app will consume two roll slots for one physical roll, making formula evaluation incorrect.

**Finding 5.2 — Sequential same-die rolling has no timeout or cancellation.**
STORY-006 confirms that rolling the same physical die N times sequentially is the intended strategy for `N×dX` with one connected die. There is no defined timeout between sequential rolls, no way for the user to cancel mid-sequence, and no state indicator showing which roll number the app is currently waiting for (e.g. "Roll 2 of 3"). Without these, the UX will feel broken whenever a user pauses between rolls.

**Finding 5.3 — `rpg-dice-roller` and actual BLE results may not align.**
`evaluateFormula(formula, rolls)` as specified in STORY-002 takes the formula string and an array of `DieRollResult` objects. The library `rpg-dice-roller` does not natively accept pre-rolled values for arbitrary formulas — its `roll()` method uses its own internal RNG. Injecting real BLE roll results into the library's evaluation engine is non-trivial and requires either: patching the roll result, using the library only for parsing + applying keep logic manually, or using the library's `RollResult` injection API if it exists. This is a significant implementation risk that is not flagged anywhere in the docs. The developer needs to verify this before STORY-002, not after.

**Finding 5.4 — Zustand `persist` with a `Map` will break.**
The spec defines the Pixels registry as `Map<pixelId, PixelEntry>` in the Zustand store. Zustand's `persist` middleware serialises state to JSON. `JSON.stringify(new Map(...))` produces `{}` — the Map is silently lost on every page reload. The `PixelEntry` also contains `pixel: Pixel` (a live SDK object with event listeners), which is completely non-serialisable. Either the pixels slice must be excluded from persistence, or the data structure must use a plain object. This architectural issue will produce a subtle bug that is hard to diagnose.

**Finding 5.5 — Windows 4-second reconnect delay workaround is unvalidated.**
STORY-003 mentions "handle the Windows 4-second reconnect delay (use `pixel.connect()` retry / `repeatConnect()` if SDK exposes it)" but the existence of `repeatConnect()` is flagged as conditional ("if SDK exposes it"). There is no fallback strategy if the SDK does not expose this. This needs to be resolved as a pre-condition to STORY-003, not an inline note.

**Finding 5.6 — `rpg-dice-roller` compound formula decomposition may not round-trip cleanly.**
`formulaToPickerState()` and `pickerStateToFormula()` must be perfect inverses for the formula text ↔ visual picker sync to work. `rpg-dice-roller` may normalise or reorder formula terms during parsing (e.g. converting `1d20+2d6+5` to a different canonical form). If the round-trip is not exact, the formula text field will visibly rewrite itself after every blur, confusing users who typed a specific notation.

**Finding 5.7 — No HTTPS enforcement story.**
CLAUDE.md and STORY-008 both note that "Web Bluetooth requires HTTPS in production." STORY-008 documents a TLS-proxy recommendation but has no AC requiring the nginx config to include an HTTPS redirect, an HSTS header, or even a comment directing operators to set up TLS. A developer who deploys STORY-008 as-is on a public host will have a broken app with no obvious reason why Bluetooth fails.

## Section 6 — Suggestions

**Finding 6.1 — STORY-002 must be preceded by a spike.**
Before any implementation begins on STORY-002, a time-boxed spike (half a day) should validate: (a) whether `rpg-dice-roller` supports injecting pre-rolled values, (b) the d% range from the Pixels SDK, and (c) whether `formulaToPickerState` round-trips reliably. The findings should update the story ACs. This is not currently captured anywhere.

**Finding 6.2 — STORY-003 should include a BLE capability detection AC.**
Add an AC: "On load, detect whether Web Bluetooth is available (`navigator.bluetooth !== undefined`); if unavailable, display a persistent banner with platform-specific guidance (iOS: use Bluefy; Firefox: unsupported; Linux: enable flag)."

**Finding 6.3 — STORY-006 should be split into two stories.**
STORY-006 currently bundles the glow/collect/evaluate engine with the Result Panel UI. Suggested split: STORY-006a (Roll engine: glow, collect BLE events, deduplication, sequential-roll state machine, evaluate) and STORY-006b (Result Panel: display, Roll Again, Close, history write).

**Finding 6.4 — Canonical die type token must be decided and documented before STORY-002 and STORY-003.**
Create a single `DieType` enum or union in `src/types/formula.ts` that is the authoritative token used everywhere. Map `pixel.dieType === "d00"` → `"d100"` at the BLE boundary. Map `"d100"` → display label `"d%"` at the UI boundary.

**Finding 6.5 — Add a "keep N > count" validation AC to STORY-005.**
When the Keep [N] input value exceeds the die count for that row, disable the Roll and Save buttons and show an inline error "Cannot keep N of M dice."

**Finding 6.6 — "Unsaved changes" guard should be a shared concern.**
Add a single AC to STORY-005: "If any field has been modified since last save, navigating away via [← Back] shows a confirmation dialog: 'Discard changes?' with [Keep editing] / [Discard]." This is a one-line React Router `useBlocker` call.

**Finding 6.7 — Manual result entry fallback needs its own story or a complete AC block in STORY-006.**
At minimum, add ACs to STORY-006: "If a die is missing or disconnects, show a numeric input per missing die face; user submits; the value is treated as the roll result for that slot." If too large, extract as STORY-009.

**Finding 6.8 — Pixels slice should be explicitly excluded from Zustand persist.**
Add to STORY-003 ACs: "The `pixels` slice is excluded from the `persist` middleware (use `partialize` option). On reload, the connected-dice list is empty and the user must reconnect."

**Finding 6.9 — STORY-004 history entry display spec needs stakeholder sign-off.**
Resolve the contradiction between the spec wireframe (label + total only) and STORY-004 AC (individual die results in the list). Recommend: history list shows label + total only; full breakdown is available only in the Result Panel.

**Finding 6.10 — STORY-008 should require a `.env.example` file.**
Add AC: "`.env.example` with `APP_PORT=80` is committed to the repository."
